# NextShelf iOS v1 — M1–M4

A native SwiftUI client for NextShelf (https://nextshelfapp.com), built
fresh against the existing API. New Xcode project, iOS 17+, Swift Package
Manager (no dependencies), `URLSession` + `Codable` + async/await,
cookie-session auth exactly like the web app.

**Status: code complete, NOT compiled.** This Linux VM has no Xcode, so
nothing here has been built or run. Verification happens on the cloud
Mac build (Codemagic free tier → TestFlight). See "First build" below.

## First build (on the cloud Mac)

1. Create the GitHub repo and push this folder (owner's step — the CLI
   here isn't logged in). Then connect the repo in Codemagic (free tier:
   500 macOS minutes/month).
2. Open `NextShelf.xcodeproj` in Xcode 16+.
3. **Signing:** select the owner's Apple Developer team in
   Signing & Capabilities. Bundle id is `com.nextshelf.app`. (The owner
   already has an Apple Developer account — no enrollment needed.)
4. Build (⌘B), fix whatever the compiler finds, run on a simulator,
   then archive → TestFlight.

Known first-build risks (no compiler was available here, so these are
honest unknowns, not verified):
- The handwritten `project.pbxproj` (generated by
  `tools/generate-project.py`) — validated structurally by
  `tools/validate.py`, but Xcode is the real test.
- `KeychainPasswordItem.swift` (salvaged Apple sample) uses
  `withUnsafeMutablePointer` — valid in Swift 5, but confirm no warning
  becomes an error under the project's settings.
- `WKWebView` cookie sync (both directions) is untested end to end.

## API — verified against live code, not guessed

Models were written from the backend repo (`damoateng1989-star/hub-scanner`,
main at commit `beedef5`, read Nov 8 2026): `app.py`, `board.py`,
`engine.py`, `options.py`, `gamma.py`, `paper.py`, `earnings.py`,
`patterns.py`, `auth.py`. Where live code contradicts the spec, live
code wins — the discrepancies:

1. **Regime is on `/api/board`, not `/api/info`.** The spec said
   `/api/info`; live `/api/info` has no regime field. The client reads
   `board.regime` (`{regime: "up"|"down", close, sma, index: "SPY",
   days: 50, as_of}`).
2. **Free tier currently gets the FULL board.** The spec says Free gets
   live/near as counts only. Live `board_for()` returns true while the
   `BOARD_FOR_ALL` env var is on — and it defaults to `"true"`. The
   locked path still exists. The client renders whatever the API
   returns (rows when present, locked-count card when a group is empty
   but its count is > 0), so it is correct under both settings.
3. **`/api/paper` is admin-only.** The spec's record screen includes
   paper trades view-only, but the endpoint 403s for non-admins. The
   client calls it only when `me.is_admin`, otherwise the section is
   omitted.
4. **Options plans are not Pro-only right now.** Same pattern:
   `OPTIONS_FOR_ALL` defaults to `"true"`. The client handles the 403
   (shows "Options plans are a Pro feature") for when the gate closes.
5. **No API toggles for "breakout alerts" or "pre-close warnings".**
   The mockup shows switches for both; `/api/me` exposes no such
   fields (delivery is driven by watchlist + Telegram; pre-close is a
   Pro-only type gated server-side). They render as status rows, not
   fake switches.
6. **Guest `/api/board`** returns counts for live/near/forming only
   (no `recent_count`/`setups_count`); **`/api/record` requires auth**
   (guests get the public strip from `/api/public/summary`).
7. **Google sign-in is a redirect flow** (`/auth/google` → Google →
   `/auth/google/callback` → 302 `/app`). There is no custom URL scheme
   to catch, so v1 runs it in a `WKWebView` and copies the `hs_session`
   cookie out into shared storage (`GoogleAuthWebView`).
8. **The ticker page in the web view needs the session cookie too.**
   `TickerWebView` copies cookies INTO the web view before loading
   `/t/{symbol}` — otherwise the page's own `/api/chart` call loads as
   a guest and the chart comes back empty.
9. **No `/api/me/device` endpoint exists.** That is the M5 backend
   patch (below). Web Push (`/api/push/*`) exists but is browser push,
   not APNs — not used here.

## Salvage (from Regulur — what was actually lifted)

- `Salvage/KeychainPasswordItem.swift` — lifted as-is (Apple's 2016
  Keychain sample). Standby only: v1 auth is cookies, no token stored.
- `Salvage/Extensions.swift` — Date/String/Color helpers, rewritten
  for modern Swift (the originals used removed Swift 4 APIs and
  force-unwrapped). Lineage noted in the file.
- `Theme/Theme.swift` — the `ColorsConfig` *approach* (one named-colour
  struct), re-implemented in SwiftUI with NextShelf's palette.
- `Theme/Components.swift` — the white-pill segmented control, fresh
  SwiftUI, inspired by Sparrow's segmented control pattern.
- `API/APIClient.swift` — the typed-endpoint *pattern* from Regulur's
  `Router` + `WebService`, rewritten on `Codable` + async/await with
  cookie auth instead of HTTP Basic Auth.
- NOT lifted: the UIKit PaperOnboarding flow (v1 is SwiftUI; the
  welcome screen covers the flow), the UIKit Sparrow files, any domain
  model, any Router endpoint, AppDelegate push wiring (M5), the Podfile.
- **No secret was copied.** The Regulur code contains a hardcoded
  Basic Auth password, Stripe test keys, a Google Maps key and a
  Braintree token. None of those are in this project — verified by
  `tools/validate.py` (secrets sweep) and by the fact that no file
  from Regulur's `reference/` folder was copied at all.

## Design bar

White-pill segmented tabs, clean and easy on the eyes, green/red for
direction percentages only (status/progress/LIVE/checkmarks are neutral;
see `Theme.swift`). Dark-first, light supported (system appearance).
Logo: `logo-app-icon.png` (1024) for the app icon + auth hero;
`logo-primary` / `logo-dark` lockups for the launch screen (per
appearance). Wordmark is the brand serif; UI text is the system sans.

## Product rules the client obeys

- Acts only on closes, never wicks. Displays the 1:30 PM verdict
  candle and the 4:00 PM confirmation; never invents a signal from an
  intraday move.
- Paper trading is display-only; no order placement from the app.
- No Pro purchase in-app; Pro upsell links out to the web.
- The regime filter is server-side; the client displays it, never
  computes it.
